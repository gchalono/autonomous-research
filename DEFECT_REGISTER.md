# Urgent live fix (October 28, 2026)

| ID | Severity | Defect / gap | Evidence | Status / Fix |
|---|---|---|---|---|
| D-27 | HIGH | JSON-object fallback 400: when strict structured output was rejected, the fallback request reused the user message unchanged. The Responses API requires the word "json" in the INPUT messages for `text.format.type = "json_object"`; agent user messages (e.g. "USER OBJECTIVE: ...") contain no such word (only the SYSTEM prompts say "JSON", which the API does not count), so the fallback failed with HTTP 400 and the run FAILED. First genuine live run, project `17833c7a8172`: FAILED, 0 revisions, 0 corrections, 0 tool calls, $0.0053 recorded. | User-reported live error, exact message reproduced against a fake client enforcing the same API rule. | **FIXED** — `src/llm/provider.py`: every `json_object` request now appends an explicit "Return your response as valid json only" instruction to its input; strict mode remains the preferred first attempt and its input is untouched. Strict-rejection reason is now preserved in error messages instead of being swallowed. Tests: `tests/test_json_fallback.py` (7 tests: exact-400 reproduction, fallback success with word present, strict success without suffix, fallback validation via Pydantic, malformed JSON, API error propagation, strict-error preservation). |

| D-28 | HIGH | Executor tool-call protocol failure (second live failure): the executor's tool calls travelled as model-written JSON text (ExecutorStep envelope). That envelope is enforced only in strict structured-output mode; on a strict rejection the json_object fallback guarantees valid JSON, not schema conformance. The live model drifted to bare tool-call objects -- two formats in one output (a bare "query" object and an "arguments" object) -- and concatenated them, which is not even valid JSON. `json.loads` in `provider.complete` rejected it ("model returned non-JSON output"), and `call_agent` repaired only Pydantic validation failures, so a non-JSON response got ZERO repair attempts and the run FAILED. Zero tool calls were recorded because nothing ever reached dispatch: parse failure preceded dispatch. Live project `c9b4973708ec`: FAILED, 1 prompt revision, 0 corrections, 0 tool calls, $0.0126. | User-reported live error with exact output text; reproduced against the provider (concatenated text -> LLMError non-JSON). | **FIXED** — native Responses API function calling for the executor (`OpenAIProvider.create_tool_response`, `agents/executor.py::run_execution_native`): tool calls arrive as discrete API items, the final report as a Pydantic-validated `submit_report` call; model prose/JSON text is never parsed on this path, so the concatenated-JSON class cannot occur. Every action is validated before dispatch (unknown tools, unparseable or invalid arguments become error outputs, never executions). Legacy JSON-step loop kept for non-native clients, and now gets one repair attempt for non-JSON output instead of failing immediately. Tests: `tests/test_tool_protocol.py` (15 tests). |
